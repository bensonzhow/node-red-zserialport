# 12 表位重复通讯与进程回收测试（Windows 7）
本次通过台体软件原有 IoT-swift 流程测试 12 个表位。监测工具在独立窗口记录进程和内存，停止 IoT-swift 后也要继续采样。请记录现场电脑显示的时间，精确到秒。

## 1. 准备
在允许暂停台体测试的时段操作。将整个交付包解压到可写目录，以下假设为 D:\serial-check。目录中应有 node-zserial-1.0.44.tgz、monitor-sync.cmd 和 monitor-sync.ps1。保留 tgz 原样。备份现场原 flows.json、项目包配置和原插件安装包，以便恢复。使用现场已配置的业务流程及同一批表位。

## 2. 先开监测窗口，采集基线
打开一个独立的管理员 CMD，执行：
```cmd
cd /d D:\serial-check
monitor-sync.cmd
```
看到 Log: 后面的完整路径就保持窗口打开。约每 2 秒采一次，屏幕安静是正常的。在资源管理器确认同目录生成 sync-monitor-日期-时间-PID.csv，等至少 10 秒再继续。用记事本查看副本，确认有以 OK 结尾的数据行；若持续 ERROR 或未生成 CSV，先保留报错，检查目录写权限和 Windows WMI 服务。在另一个窗口执行后续操作。记录测试前已有的桥接进程，便于区分上一轮残留。

## 3. 离线安装并核对插件
等台体空闲后，按现场运维方式停止运行该流程的 IoT-swift 服务。打开第二个 CMD，进入该服务实际使用的用户目录。此前该台体日志中的目录如下，若安装位置不同，请替换第一行。
```cmd
cd /d C:\energy-meter-sorting\resources\swift\nodejs\user-swift
npm install --offline --no-audit --no-fund "D:\serial-check\node-zserial-1.0.44.tgz"
node -p "require.resolve('node-zserial/package.json')"
node -p "require('node-zserial/package.json').version"
```
路径应指向本台体用户目录下的插件，版本应为 1.0.44。若现场直接运行 node 提示 Win7 平台检查，在此 CMD 先运行 set "NODE_SKIP_PLATFORM_CHECK=1" 再执行上述命令。若 npm 或 node 不在 PATH，使用现场配套的 npm.cmd、node.exe 完整路径。安装报错请保存终端输出。确认安装成功后，按原方式启动服务。监测窗口保持运行。

## 4. 从台体界面运行原测试
确认实际发送给“批量发收”的串口配置使用 backend: 'win32-sync'（批量请求为 msg.serialConfigs 每一项）。从原测试界面启动任务，保持 12 个表位、相同电表、通信参数和原测试节奏。每轮完成后再启动下一轮，持续超过以往出错的轮数。例如以前第 3 轮出错，本次可先连续跑 5 轮。记录每轮开始、结束时间、通过表位和失败表位。轮次之间保持原操作方式。单纯启动服务不一定会打开端口，实际数目取决于业务流程何时打开或释放连接。

## 5. 中途故障与结束采样
出现首个 1450 时，立即记下时间、表位和 COM，保留完整错误（尤其 bridgePid、openAttemptId、attempt、bridgeVersion；新版辅助程序为 1.0.44-sync3）。让当轮原有重试完成并记下结果。采集期间避免手动杀进程或重启电脑，以保留回收现场。
   
无论成功还是失败，等本轮结束、设备处于可停机状态，记录停止时间，按原方式停止 IoT-swift 服务。确认服务未自动重启，监测窗口再保持 **至少 30 秒**。重点看属于本次 Node PID 的桥接 PID 是否消失；同机其他服务的进程应按父 PID 区分。若仍有残留，在第二个 CMD 将快照保存到测试目录：
```cmd
wmic process where "name='zserial-sync.exe' or name='node.exe'" get Name,ProcessId,ParentProcessId,CreationDate,ThreadCount,HandleCount > "D:\serial-check\after-stop.txt"
```
回到监测窗口按 Ctrl+C 停止，提示是否终止批处理时输入 Y。若本轮全部正常，可按原方式重新启动服务，用相同流程再跑一轮验证重新打开；需要采集此轮时先重新启动监测，会生成第二份 CSV。测试结束后按现场安排恢复服务。

## 6. 发回材料
请将下列文件一起压缩发回。通过的轮次同样保留。
- 所有本轮 sync-monitor-*.csv 原文件。
- 同时段 error.log、systemRuninfo.log，以及失败表位和至少一个正常表位的 meters 日志。
- 若有残留，附 after-stop.txt。若现场修改过流程，再附实际部署版本的 flows.json。
- 现场记录：台号、12 表位对应 COM、插件版本、各轮起止时间和结果、首次错误时间、服务停止时间、停止 30 秒后残留 PID、是否发生自动重启或手动干预。

CSV 的 bridgeCount 为全机桥接进程总数，bridges 列按 PID/父PID/创建时间/句柄数/私有内存MB 记录，nodePIDs 为全机 Node 进程。status=ERROR 的行表示采样失败。以每轮通讯结果、停止服务后本轮 PID 的去向及服务重开后能否继续通讯作为验收依据。
